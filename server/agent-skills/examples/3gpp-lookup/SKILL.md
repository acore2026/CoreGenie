# 3GPP 快速查询

用最少的官方资料回答简短事实问题。不要把快速查询扩展成提案下载或研究报告任务。

## 工作方式

1. 涉及会议号时，先调用 `3gpp.resolve-meeting`。精确日期或会场问题保留 `include_invitation=true`。不要猜测 FTP 目录名称。
2. 优先使用解析器返回的会议目录和 `officialDetails`；这些信息足够回答时不得继续浏览子目录。
3. 只有现有信息不足以回答时，才用 `web.fetch` 打开解析器返回的官方链接或它的直接子目录。
4. 已获得能够回答问题的一项官方证据后立即结束；精确日期、状态等容易混淆的事实可以再核对一项官方资料。

## 约束

- 不运行 Bash 或 Python，不临时安装依赖。
- 用户没有明确要求时，不下载提案、不创建文件、不写知识库。
- 会议目录能确认月份和地点，但不能确认具体日期时，应再查官方日历、议程或邀请函；无需解析附件就能回答时，不下载附件。
- 官方资料只有 PDF 且当前工具无法直接提取时，说明已确认到的范围，不要为了一个简单问题启动完整文档处理流程。
- HTTP 401、403 或 404 后不要原样重试，也不要尝试目录别名；返回工作组父目录确认真实链接。
- 公司提案不等于 3GPP 已采纳的结论。状态问题必须查看会议结果或正式材料。

## 工作组目录

`3gpp.resolve-meeting` 已内置这些规范目录：

| 工作组 | 目录 |
| --- | --- |
| SA1 | `tsg_sa/WG1_Serv` |
| SA2 | `tsg_sa/WG2_Arch` |
| SA3 | `tsg_sa/WG3_Security` |
| SA5 | `tsg_sa/WG5_OAM` |
| CT1 | `tsg_ct/WG1_NAS` |
| CT4 | `tsg_ct/WG4_PROCO` |

找不到会议时，报告已检查的规范父目录和缺失信息，不要构造其他路径。
