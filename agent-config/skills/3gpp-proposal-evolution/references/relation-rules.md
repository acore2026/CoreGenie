# 前后关系

先区分关系类型，再标证据等级，不能把二者混为一谈：

- 明确关系：原文明确写出修订、基于、重新提交或合并对象；保留原话、TDoc 和位置。`based_on`、普通引用和 `merged_into` 都不是 `revision`。
- 强候选：实际修改章节、技术机制和至少一项独立正文连续证据相符，排除公共基线文字相似后仍成立。由分析确认，脚本不自动给出。
- 同主题候选：仅有章节、变体、标题等主题重合，尚未证明直接延续。

工作组、Release、WI、TR/TS 不一致时先检查范围，不能仅凭 KI18 或 18.16 关联不同研究。章节可能重编号；标题可能列出多项变体，实际正文只修改其中一部分。以实际修改章节为准。公司署名仅作辅助，不把联合稿视为每家公司独立主张。

明确修订构成有向链；合并、拆分和跨会议延续允许多对多，但必须保留各自类型。普通正文引用只说明引用关系。缺少的中间 TDoc 保留为未获取节点，不跳过它声称直接修订。环、重复编号、反向会议引用或冲突元数据需报告，不随意修复。

DOCX 提取复用 review 的 source index、正文块和修订记录。用于判断当前建议的文本排除删除和 moveFrom，保留新增和 moveTo；同时保留原始删除、新增内容供变化分析。表格、图像、嵌入对象和章节不能丢弃。不得把简单拼接 XML 文字当作干净正文。看不清的图明确说明，不补画。非 DOCX 按 review 能力处理，无法提取时保留缺失状态。

未找到上一会议匹配只能称“本资料范围内未找到前稿”，不能直接认定首次提出。新增技术内容必须比较真实修改段落，并区分已有 TR 基线和作者新建议；需要中间 TR 版本才能判断时明确列出。

`Revised` 只说明修订，`Not Handled` 不是否定，`Withdrawn` 不是被拒绝；`Merge into` 是合并记录，不证明每项内容保留。只有会议材料明确批准且相关内容存在于批准稿，才说明该内容通过。保留原稿和后稿各自状态。
