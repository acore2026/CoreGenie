# 3GPP 会前简报：离线演示材料

**以下全部为虚构演示材料，非真实 3GPP 文稿。** DEMO-A/B/C 不是 TDoc 编号，团队甲/乙/丙不是实际公司。没有对应真实会议、TR/TS 或会议采纳结论。情景采用无线接入技术讨论的写法，目的是展示资料读取、立场比较、来源引用和会前简报。

## DEMO-A：由终端提供业务时序提示

来源：团队甲（虚构）。主题：面向交互业务的时序提示。

### A1：主张
终端在获得网络配置后，可报告业务数据的周期性和时限区间，帮助网络选择调度策略。团队甲主张先研究由终端显式提供提示的方案，不要求上报应用名称或完整应用标识。

### A2：触发与代价
报告应为可选能力，在业务开始或已报告的时序特征发生明显变化时触发。需要评估额外上行信令、终端能耗以及时限区间过细可能带来的隐私风险。材料没有给出量化收益或额外信令开销的测试结果。

### A3：回退与边界
当终端不支持报告、业务无法提供可靠时序信息或网络未配置报告时，继续采用不依赖这些提示的处理方式。材料没有评价“网络独立推断时序”是否可行，也没有反对该方案。

## DEMO-B：优先利用网络侧观测

来源：团队乙（虚构）。主题：基于网络观测推断业务时序。

### B1：主张
网络可以先利用已观测到的数据包到达时间和队列状态推断周期性，在推断置信度满足部署要求时不新增终端报告。团队乙支持先评估网络侧方法，避免在收益不明确时增加终端信令。

### B2：例外条件
对于突发业务、冷启动或观测不足的情形，材料允许进一步研究终端辅助信息，但要求证明额外信令能带来可衡量的收益。因此，团队乙没有全面反对终端辅助报告。

### B3：待验证问题
需要测试突发流量下的推断可靠性、冷启动时间以及不同业务混合后的表现。材料没有规定报告字段、统一的置信度阈值或时限区间粒度，也没有给出任何已完成的实验数值。

## DEMO-C：由网络按需请求粗粒度提示

来源：团队丙（虚构）。主题：网络观测与可选终端提示的组合。

### C1：主张
优先利用网络侧观测；在网络认为现有观测不足时，由网络配置终端上报粗粒度周期性和时限区间。提示字段不包含应用名称，不要求连续上报。

### C2：控制与条件
报告频率由网络控制，终端在能力或权限不满足时可不提供提示。具体触发阈值和报告粒度需要后续评估。团队丙认为两类方法可以组合，但这只是该演示提案的主张，并不证明其他团队已接受组合方案。

### C3：评估与状态
建议对比“仅网络观测”“终端显式提示”“按需组合”在相同场景下的效果，同时统计时延、信令和终端能耗。当前没有测试结果、会议决定或通过状态。
